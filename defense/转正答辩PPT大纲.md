## 答辩主线

本页用一段话讲清整场答辩逻辑：

> 扫地机器人感知需要 BEV 语义理解，但受单 RGB 相机 + 激光雷达、无真实标注数据、无确定硬件方案三个限制约束。本实习通过 Habitat + Replica 自建虚拟数据闭环，完成 BEVFusion 迁移与可行性验证；再从配置和代码两个层面轻量化，形成精度、速度、体积、显存均优于基线的可部署方案，并为真机验证和后续落地做好准备。

### P3 背景与挑战

- 页面标题：车端 BEV 能否在扫地机器人上落地？
- 内容要点：
  - 扫地机器人需要基于感知结果完成语义理解，BEV 表达天然适合机器人局部地图与规划
  - 选择 BEVFusion 作为基线：相机 + 激光雷达融合、BEV 分割能力成熟
  - 三个限制条件：单 RGB 相机 + 激光雷达；无带标注真实数据；硬件方案未确定
- 核心问题：在上述约束下，验证可行性并给出可部署的轻量方案

### P6 BEVFusion 迁移适配

### P7 训练与可行性验证

- 页面标题：虚拟数据上验证了车端 BEV 的可行性
- 内容要点：
  - 训练设置：AdamW、fp16、early stopping、best checkpoint 保存
  - 展示训练 loss / val IoU 曲线
  - 展示测试集 BEV 分割结果与 GT 对比
  - 基线指标：IoU@max 0.428、端到端 49.5ms、20 FPS
- 结论：车端 BEV 能够迁移到扫地机器人配置，但模型体积、延迟、显存仍需轻量化

### P8 轻量化设计

- 页面标题：配置层和代码层两条路径并行
- 内容要点：
  - 配置层 a1-a6（a2 按约定排除）：LSS 分辨率、depth bin、分割头通道、Swin 深度、lidar 分辨率
  - 代码层 b1/b2/b6：Pillar + 2D BEV 编码器、轻量分割头、MobileNetV2 相机骨干
  - 组合实验：b1a3、b1a4、b1a3a4
- 素材：改动点对照表 + 实验组合矩阵图
- 讲述重点：先单模块评估，再组合收敛，避免一次改太多无法归因

### P9 轻量化结果（核心数据页）

- 页面标题：最优方案在精度、速度、体积、显存上全面占优
- 内容要点：
  - 统一口径：虚拟测试集、NVIDIA L40、fp16、batch=1
  - 基线与最优组合对比表

| 指标 | 基线 | 最优组合 b1a3a4 |
| --- | ---: | ---: |
| 参数量 | 42.6M | 35.9M |
| 模型体积 | 162.9MB | 137.0MB |
| 端到端延迟 | 49.5ms | 28.6ms |
| FPS | 20.2 | 35.0 |
| model-only 延迟 | 42.9ms | 23.7ms |
| 前向峰值显存 | 416.6MB | 308.4MB |
| 训练峰值显存 | 2880MB | 2155MB |
| BEV mIoU@max | 0.428 | 0.528 |

- 补充结论：b1 单独方案精度更高（0.538），b1a3a4 在速度/体积/显存上更均衡
- 素材：精度-延迟散点图、模型体积柱状图、显存对比图
- 讲述重点：轻量化不是单纯变小，而是在保持精度前提下优化部署资源

### P10 部署性能与问题定位

- 页面标题：定位并绕开 3D 稀疏卷积显存异常
- 内容要点：
  - 开发 tools/benchmark_robot_bev_deployment.py 统一评测延迟、FPS、显存、吞吐
  - 现象：推理阶段显存从 2GB 左右缓慢增长后跳变到 16GB
  - 定位：问题集中在 3D SparseEncoder 推理路径，base/a*/b2/b6 均复现
  - 解决：b1 使用 Pillar + 2D BEV 编码器绕开该路径，部署显存稳定在约 2.9GB
  - 待办：修复该 bug 后重测 base/b2/b6，确认真实收益
- 素材：显存变化曲线图、问题路径标注图
- 讲述重点：体现独立定位、复现和规避问题的工程能力
