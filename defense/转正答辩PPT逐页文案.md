## P3 背景与挑战

- 页面标题：扫地机器人需要 BEV 感知，但车端方案能否直接迁移？
- 副标题：面向单 RGB 相机 + 激光雷达配置，缺少带标注真实数据
- 内容要点：
  - 扫地机器人需要理解 floor、carpet、wall、furniture、door、clutter 等局部语义，支撑避障、导航和清扫策略
  - BEV 表达将相机与激光雷达统一到俯视坐标系，天然适配机器人局部地图和规划
  - 选择 BEVFusion 作为基线：相机 + 激光雷达融合、BEV 分割能力成熟
  - 关键挑战：
    - 车端 BEVFusion 通常面向多相机配置，需要迁移到单 RGB 相机 + 激光雷达
    - 缺少带标注真实数据，需要自建虚拟数据闭环
- 核心问题：在以上约束下，验证可行性并形成可部署的轻量方案

讲述稿：

扫地机器人的感知任务适合用 BEV 来表达，但车端 BEV 算法能否迁移到室内机器人，需要回答两个问题：一是单目相机加激光雷达的配置是否够用，二是在没有真实标注数据时如何完成训练验证。这也是我整个实习的出发点。

## P8 轻量化设计

- 页面标题：配置层与代码层两条路径，单模块评估 + 组合收敛
- 配置层改动：
  - a1：LSS 直接生成 4cm BEV，downsample=1
  - a3：depth bin 步长从 0.05m 增至 0.10m
  - a4：分割通道从 512 降至 256
  - a5：LiDAR 1cm 体素并减少一级编码
  - a6：Swin depths 从 2262 调整为 2242
- 代码层改动：
  - b1：LiDAR 使用 Pillar + 轻量 2D BEV 编码器
  - b2：低分辨率分割 + 边界细化头
  - b6：相机骨干替换为 MobileNetV2
- 组合实验：b1a3、b1a4、b1a3a4
- 设计原则：先单模块评估，再组合收敛，避免一次改太多无法归因

讲述稿：

轻量化我采用了两条路径：配置层通过修改参数快速验证，代码层通过替换网络结构获得更大收益。每个模块单独评估后再组合，最终收敛出部署性价比最高的方案。

## P9 轻量化结果（核心数据页）

- 页面标题：最优组合在精度、速度、体积、显存上全面优于基线
- 统一评测口径：虚拟测试集、NVIDIA L40、fp16、batch=1

| 指标 | 基线 | b1 | b1a3a4 |
| --- | ---: | ---: | ---: |
| 参数量 | 42.6M | 40.0M | 35.9M |
| 模型体积 | 162.9MB | 152.7MB | 137.0MB |
| 端到端延迟 | 49.5ms | 29.7ms | 28.6ms |
| FPS | 20.2 | 33.7 | 35.0 |
| model-only 延迟 | 42.9ms | 24.9ms | 23.7ms |
| 前向峰值显存 | 416.6MB | 404.0MB | 308.4MB |
| 训练峰值显存 | 2880MB | 2735MB | 2155MB |
| 测试 mIoU@max | 0.428 | 0.538 | 0.528 |

- 补充结论：
  - b1 单独方案精度最高
  - b1a3a4 在速度、体积、显存上更均衡，适合作为部署首选
  - 相对基线：模型体积 -16%，延迟 -42%，FPS +73%，mIoU@max +23%
- 图表建议：精度-延迟散点图、模型体积/显存柱状图、FPS 对比图

讲述稿：

轻量化的核心结论是：精度与效率可以兼得。最优组合 b1a3a4 在虚拟测试集上 mIoU 从 0.428 提升到 0.528，同时模型体积减少 16%，端到端延迟从 49.5ms 降到 28.6ms，FPS 从 20 提升到 35。如果更看重精度，b1 单独方案是更好的选择。

## P10 部署性能与问题定位

- 页面标题：统一部署基准，定位并绕开 3D 稀疏卷积显存异常
- 内容要点：
  - 开发 tools/benchmark_robot_bev_deployment.py，统一评测延迟、FPS、显存和吞吐
  - 发现现象：推理阶段显存从 2GB 左右缓慢增长后跳变到 16GB
  - 定位结果：问题集中在 3D SparseEncoder 推理路径
  - 影响范围：base、a 系列、b2、b6 均复现
  - 解决方式：b1 使用 Pillar + 2D BEV 编码器绕开该路径，部署显存稳定在约 2.9GB
  - 待办：修复该问题后重测 base/b2/b6，确认真实部署收益
- 图表建议：显存随时间变化曲线、问题路径标注图

讲述稿：

在部署评测过程中，我发现 3D 稀疏卷积推理时存在显存异常增长的问题，会从 2GB 跳变到 16GB。通过统一基准工具我完成了复现和定位，并确认 b1 的 Pillar 方案可以绕开这条路径。这个问题既影响了部署结论，也说明需要后续修复后重新评估其他方案。
